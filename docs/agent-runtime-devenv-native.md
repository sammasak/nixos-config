# Devenv configuration in the nspawn runtime (devenv-platform#93)

This test evaluates a pinned Devenv project and executes its configured check
inside the existing agent-runtime nspawn guest. It does not realize the full
Devenv-generated shell environment yet; the guest toolchain is explicitly
listed from the same pinned nixpkgs packages as the fixture.

## Fixture and execution

`tests/fixtures/devenv-native` requires Devenv `2.4.0`. Its `devenv.lock` pins
the Devenv module input to `9655d320b8f9df74dbecf681f52a7334574606c3` and
nixpkgs to `fe13242281a67641c0102cdb1087f0ebe586c7df`. The YAML imports
`./tooling`; that module exports `DEVENV_IMPORT_MARKER`. The project also
defines an `enterShell` hook that writes `.devenv-enterShell-ran` under
`DEVENV_ROOT`. Host-side evaluation sets `DEVENV_ROOT` to its temporary
fixture and asserts that this marker was not created, so the test checks that
preparation did not enter the project shell.

The test derivation copies the fixture to a temporary project and, offline,
uses Devenv to evaluate `scripts.check.exec` and
`env.DEVENV_IMPORT_MARKER`. It asserts both are present and that the imported
marker has the expected value. It also asserts the `enterShell` marker is
absent after evaluation. This evaluation does not enter the shell or run
project hooks on the host. The VM runner loads the evaluated script and marker,
sets `DEVENV_ROOT` to the guest's writable `/workspace/fixture`, then executes
the exact script there. The script checks the imported marker, writes
`.devenv-script-ran`, and runs `make check`. The harness does not create that
Devenv-defined marker.

The offline evaluator now also runs two isolated mutation probes on every
build: it removes the YAML import and requires the imported marker lookup to
fail with the missing `DEVENV_IMPORT_MARKER`; then it removes only
`scripts.check.exec` while retaining `devenv.nix` and requires both Devenv
evaluation and the non-empty script extraction guard to fail. This prevents a
stale fixture, ignored YAML imports or a missing project check from passing the
normal test entrypoint. Separate manual mutations against published `9342aae`
previously demonstrated the same boundaries.

## Runtime behavior and limits

Mode (a) runs the configured check with the fixture's explicitly projected
`gnumake`, `gcc` and `coreutils` inside the guest. The existing admission,
network and credential denial, read-only store, capability/seccomp boundary,
resource quotas, broken-source behavior, lifecycle, recovery and cleanup tests
remain in the VM suite.

Mode (b) attempts `devenv --offline … shell -- true` from the fixture root
inside nspawn. The runtime has no Nix daemon socket, exposes `/nix/store`
read-only and allows only loopback networking. Nix falls back to a private
store under the guest's quota'd home and fails while importing the locked
nixpkgs tree with `No space left on device`. The command and structural reasons
are recorded in `mode-b.log`; the test checks the failure is not caused by a
missing project file. No host Nix socket or writable host store is exposed.

This PR is configuration/script acceptance evidence, not complete #93 closure.
The separate native-shell path and later generated-environment path extend the
same bounded nspawn lifecycle without changing this PR's explicit-toolchain
test contract. Keep the cold guest-side Nix activation limitation below in
view; those follow-on paths realize the environment on the host.

## Follow-on implementation status (2026-11-09)

The original follow-up items have since been implemented in separate PRs:

- [nixos-config#188](https://github.com/sammasak/nixos-config/pull/188) adds a
  native flake `mkShell` mode that evaluates the repository's own `flake.lock`
  on the host and runs its gate inside nspawn. It is complementary to this
  PR's `devenv.yaml` fixture and explicitly projected matching toolchain; the
  two PRs touch separate files and have no merge dependency.
- [nixos-config#192](https://github.com/sammasak/nixos-config/pull/192) projects
  the complete environment generated by Devenv, including project variables,
  imports and `enterShell`, into the existing guest lifecycle. Host preparation
  now uses a scrubbed environment and root-managed Devenv/Nix executables.
- [nixos-config#193](https://github.com/sammasak/nixos-config/pull/193) consumes
  typed execution requests and rejects blocked or mismatched provenance before
  project activation.
- [nixos-config#194](https://github.com/sammasak/nixos-config/pull/194) runs
  Factum's locked test request through that path. Its current descendant stack
  passed `nixos:qa` at `db947d25a3e3fe55b01675189b57f4e36a826807` in 502 seconds;
  `secrets-verify` skipped because Acer has no readable age key, while
  `worker-permissions-test` and the other QA tasks passed.

These PRs are still open for normal review and merge. MSI real-host resource
measurements and runtime acceptance also remain pending: Acer currently has no
network route to `192.168.10.235`. The cold guest-side activation limitation
remains unchanged; none of the follow-on work adds a private guest store.
